# SIMNET Autonomous AI Operator — Standalone Chat

Отдельное Chrome MV3-расширение для ручного тестирования диалога **от лица абонента**. Собирается из проверенных исходников AI Operator, но после сборки устанавливается как **самостоятельное расширение** (собственный extension ID, chrome.storage и UI). Основной SIMNET Workbench не изменяется.

## Сборка и запуск

Нужен Node.js 20+ и локальная копия репозитория.

```powershell
cd "$env:USERPROFILE\Desktop\simnet-workbranch"
git fetch origin
git switch feat/standalone-ai-operator-chat
git pull --ff-only
node .\scripts\build-standalone-ai.mjs
node --test .\tests\standalone-ai-smoke.test.mjs
```

Открыть `chrome://extensions` → включить режим разработчика → **Загрузить распакованное** → выбрать `dist/ai-operator-standalone`. Закрепить SIMNET AI Operator на панели Chrome и нажать значок для открытия отдельного чата.

1. В панели «Настройки» ввести **свой DeepSeek API-ключ** и выбрать модель. Ключ из Workbench не переносится.
2. Нажать «Проверить API» — эта проверка подтверждает лишь доступность API, не корректность всего AI-цикла.
3. Для live-READ открыть вкладки Billing/UserSide и войти в них как обычно. Новый агент **не обходит авторизацию** и **не получает чужую сессию**.
4. Писать вопросы от лица абонента. Наблюдать справа источники и коды результатов READ. «Новый диалог» очищает историю, контекст личности и слепки старого случая, сохраняя API-настройку.

## Архитектура и границы

```text
standalone-ai/chat.html + chat.js
        ↓ AI_OPERATOR_LAB_SEND
standalone-ai/background.js
        ↓ import
src/features/ai-operator/lab-background.js
        ↓ semantic-probe → SIMNET knowledge/instructions
        ↓ semantic-tool-broker → canonical facts/decision rules
        ↓ live-tool-runtime → Billing / UserSide / network READ
        ↓ evidence check → ответ в отдельном чате
```

- **Runtime-изоляция:** отдельное расширение, отдельные настройки, ключи, история и storage. Никакой миграции пользовательских данных из Workbench.
- **Build-time reuse:** импортируем существующие модули, не делаем второй альтернативный resolver/KB/policy. Сборщик рекурсивно копирует импортируемые файлы в `dist/ai-operator-standalone`. Сам пакет не зависит от установленного Workbench.
- **READ-only:** Standalone не загружает модуль обычного AI Operator/HelpCrunch polling, действие SEND, CALL или content scripts Workbench. Доступные LIVE-тулы ограничены действующими READ-реализациями.
- **Источники:** Billing, UserSide и network-информация через существующие авторизованные вкладки браузера. Открытая вкладка ≠ подтверждённая сессия; успех определяется результатом конкретного запроса.
- **Разделение фактов:** ADDRESS ≠ CONTRACT ≠ PERSON, `UNKNOWN ≠ FALSE`. Старый snapshot не считается доказательством актуального состояния.
- **LLM:** DeepSeek понимает смысл/контекст и формулирует ответ; вычисления, источники и критичные правила контролирует код. Это не отдельное fine-tuning обучение модели.
- **API:** ключ сохраняется локально в профиле Chrome средствами `chrome.storage.local`. Его безопасность зависит от безопасности пользовательского устройства и профиля; расширение не является хранилищем уровня серверного secret vault.

## Минимальные проверочные диалоги

| Сценарий | Что должно происходить |
| --- | --- |
| «Какой у меня баланс?» без договора | Уточнение идентификатора; никакой выдуманной суммы |
| Адрес с опечатками/сокращениями | Канонизация и lookup; неоднозначность не маскируется |
| По адресу несколько договоров | Не приписывать найденный договор говорящему |
| Старый отрицательный баланс | Не требовать оплату автоматически; отдельная финансовая проверка |
| «У меня нет интернета» после уточнений | Нужные live READ и вывод только из полученного evidence |
| Новый диалог после предыдущего абонента | Нет повторного использования identity/toolState/history/snapshots |

## Статус и ограничения

Ветка содержит исходную standalone-сборку, smoke-тесты и интерфейс. **Интеграция с реальными авторизованными вкладками, фактические ответы DeepSeek, полный Scenario Replay, поведенческие регрессии и безопасность организации требуют отдельной проверки на рабочем окружении.** Отдельное окно не равно самостоятельному серверу или доступу к Billing без браузера.

Для промышленного внедрения нужны авторизация рабочего места, безопасное управление API-ключами, логирование без персональных данных, лимиты стоимости, контроль доступа, аудит действий и согласование источников данных.
