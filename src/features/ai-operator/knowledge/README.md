# SIMNET Knowledge Library

Это внутренняя энциклопедия автономного оператора, а не конечный автомат, phrasebook или свалка готовых ответов.

## Принцип

1. Сначала модель свободно понимает человеческий диалог.
2. Retrieval предлагает несколько потенциально релевантных статей.
3. Модель сама решает, какие из них действительно полезны, и может не использовать ни одной.
4. Статья описывает SIMNET: понятия, подтверждённые условия, связанные источники данных и границы достоверности.
5. Статья не должна содержать маршрутизацию вида «если клиент написал X — обязательно сделай Y».
6. Мы пополняем не набор фраз, а знания: одно подтверждённое правило должно работать для множества разговорных формулировок.

## Утверждённая классификация

База знаний делится по предметным доменам. Центральный `index.js` собирает их в единую библиотеку.

Текущие верхнеуровневые разделы:

- `billing` — баланс, платежи, идентификация, финансовая логика и значения полей Billing;
- `tariff` — тарифы, скорости, повышение/понижение, будущий тариф;
- `promotion` — акции, скидки, промоусловия и границы их применения;
- `technical` — Wi-Fi, Ethernet, PON, оборудование, гигабит, диагностика и технические понятия;
- `service` — дополнительные услуги;
- `connection` — условия и сценарии подключения.

Физически один раздел может пока храниться в одном `.js`-файле. Разбивать каждый подраздел на отдельный файл нужно только когда объём действительно этого требует. Логическая классификация определяется прежде всего стабильным `id` статьи.

Примеры стабильных ID:

- `billing.balance`
- `billing.identification`
- `tariff.residential`
- `tariff.upgrade`
- `promotion.new-connection-89x3`
- `technical.gigabit-equipment`
- `technical.wifi-vs-internet`

Формат ID: `<domain>.<topic>`. Уже используемый ID без необходимости не переименывается: он является устойчивой ссылкой для retrieval, диагностики и regression-тестов.

## Формат статьи

Каждая статья содержит:

- `id` — устойчивый машинный идентификатор;
- `title` — понятное человеку название;
- `summary` — кратко, какое знание находится внутри;
- `tags` — разговорные и предметные признаки для retrieval, включая естественные варианты формулировок;
- `text` — подтверждённое знание, условия применения, исключения и то, чего из него нельзя автоматически заключать.

`tags` не должны превращать систему в phrasebook. Они помогают найти смысловую область, а решение о применимости статьи остаётся за моделью.

## Правило пополнения KB

Любой обнаруженный пробел проходит один и тот же цикл:

`реальный диалог / replay → обнаруженный GAP → классификация → проверка существующих статей → расширение или новая статья → tags → regression → повторный тест`

Перед добавлением нового знания обязательно определить:

1. К какому домену оно относится.
2. Есть ли уже статья, которая описывает тот же смысл.
3. Является ли это общим правилом SIMNET или live-данными конкретного абонента.
4. Какие условия и исключения обязательны, чтобы правило не применялось слишком широко.

Если подходящая статья уже есть — расширяем её. Новую статью создаём только для отдельного понятия или самостоятельного правила.

Нельзя автоматически складывать операторские заметки или экспортированные GAP-записи в production KB. Сначала они проходят нормализацию, дедупликацию и распределение по статьям.

## Regression как часть знания

Исправление считается полноценным не тогда, когда заработала одна конкретная фраза, а когда подтверждённое знание корректно находится и применяется для класса похожих запросов.

После добавления или изменения важного правила добавляется regression-кейс. Он должен проверять не единственную заученную формулировку, а несколько естественных вариантов вопроса, где это оправдано.

Нельзя ради зелёного теста ослаблять старые assertions, удалять тест или подменять ожидаемое бизнес-правило текущим поведением реализации.

## Достоверность

В разговоре всегда разделяются:

- `customer_claim` — что сообщил клиент;
- `operator_claim` — что написал прошлый оператор;
- `knowledge` — подтверждённое внутреннее знание из энциклопедии;
- `observed_fact` — факт, прочитанный из Billing/UserSide/BRAS/ONU/другого READ-инструмента;
- `hypothesis` — допустимое предположение, которое нельзя выдавать за подтверждённый факт.

Энциклопедия не подтверждает состояние конкретного договора. Для персональных значений и текущего состояния нужны актуальные READ-источники.

Пример: статья может подтверждать, что для нового подключения существует акция `3 × 89 грн`, но применимость акции к конкретному договору нельзя автоматически обещать без соответствующего основания.

## Что не является статьёй KB

Не нужно создавать статьи для:

- текущего баланса конкретного абонента;
- его текущего тарифа, IP, MAC, ONU, OLT или состояния сессии;
- результата конкретного платежа;
- одноразового текста ответа;
- случайной фразы оператора без подтверждённого правила;
- каждого нового варианта формулировки одного и того же вопроса.

Такие данные либо приходят из live READ-инструментов, либо служат тестовым материалом для уже существующего знания.

## Экспериментальный Replay

На этапе `knowledge_probe` Replay намеренно НЕ использует:

- `fact-runtime.js`;
- `fact-catalog.js`;
- `dialogue-state.js`.

Они остаются в репозитории как прежний контрольный вариант, но не регулируют понимание или выбор статей.

Текущий эксперимент проверяет два вопроса:

1. Поняла ли модель, чего хочет человек и к чему относится его реплика?
2. Умеет ли она использовать внутреннюю энциклопедию только там, где она действительно добавляет полезный контекст, не придумывая новые правила и преждевременные выводы?
