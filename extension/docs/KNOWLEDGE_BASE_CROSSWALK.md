# SIMNET Workbench: карта пересечений с базой знаний

## Что было проанализировано

Источник: Google Docs «База знань оператора абонентського відділу Simnet/Looknet (2025)».

- 58 страниц.
- 537 содержательных текстовых блоков.
- 65 заголовков.
- 130 встроенных изображений.
- Разделы по Billing, UserSide, финансовым операциям, дополнительным услугам и технической диагностике.

Особенно полезны технические разделы на страницах 30–56: точка коммутации, активность оборудования, Juniper, Ethernet, PON, уровни сигнала, Static IP, медиаконвертер, телевидение и регистрация MAC.

## Предлагаемая модель режимов

### 1. Автоматическая диагностика

Это текущий Workbench:

- оператор вводит договор;
- расширение находит абонента;
- собирает данные из UserSide и Billing;
- определяет OLT и ONU;
- опрашивает ONU;
- сверяет статус, Ethernet-link, MAC, уровни сигнала и историю отключений;
- формирует вывод.

Цель: готовый диагностический результат с минимальным числом действий оператора.

### 2. Наставник

Отдельный учебно-практический режим:

- не заменяет действия оператора;
- определяет текущую карточку абонента и тип подключения;
- показывает следующий рекомендуемый шаг;
- объясняет, зачем выполняется проверка;
- отмечает уже подтверждённые действия;
- задаёт контрольные вопросы;
- ветвится в зависимости от результата;
- в конце формирует краткий чек-лист проведённой диагностики и данные для заявки.

Цель: научить оператора правильному процессу и не позволить пропустить обязательную проверку.

Третий режим пока оставлен без предположений — его назначение нужно зафиксировать отдельно.

## Общая архитектура

Режимы должны использовать единый контекст абонента, но разные сценарии работы:

```text
UserSide + Billing
        │
        ▼
Общий контекст абонента
  договор, технология, оборудование,
  ONU/OLT, MAC, сессия, линк, сигналы
        │
        ├── Автоматическая диагностика
        │     сама собирает и интерпретирует данные
        │
        └── Наставник
              ведёт оператора по шагам,
              объясняет и контролирует полноту проверки
```

Переключатель режима лучше размещать в стартовом экране Workbench. Выбранный режим можно запоминать для конкретного оператора, но активный процесс одного режима не должен незаметно продолжаться после переключения в другой.

## Контекстные маршруты Billing

Наставник не показывает единый чек-лист для всего Billing. Он определяет
текущий раздел по `pathname` и query-параметру `a`, после чего ведёт оператора
по одному шагу выбранного маршрута:

| Контекст | Признак страницы | Учебный маршрут |
|---|---|---|
| Карточка клиента | `adm.pl?a=user` | идентификация → финансы → тарифы и услуги → техническая навигация → история → безопасное изменение |
| Juniper | `stat.pl?a=250` или `a=252` | сессия → IP/MAC/VLAN → время и трафик → команды → контрольная сверка |
| ONU / PON-порт | `stat.pl?a=310..313` | правильный OLT/порт → статус → сигналы → link/MAC → соседи → итог |
| Финансы | `adm.pl?a=pays` или `a=payshow` | баланс и период → цепочка событий |
| Технические данные | `adm.pl?a=dopdata` | технология → идентификаторы → OLT → следующий источник → безопасная работа с MAC |
| Трафик | `stat.pl?a=108/111` или `adm.pl?a=chanal` | период и единицы → сопоставление с жалобой |

Прогресс хранится отдельно для каждого контекста в рамках открытой страницы:
при переходе в Juniper маршрут карточки не смешивается с Juniper, а при
возврате может быть продолжен с прежнего шага.

В учебном режиме контрольные поля не раскрашиваются постоянно. Панель сохраняет
их оценку, а кнопка показа включает фокусный сценарий:

- вся рабочая область Billing затемняется нейтральным серым слоем;
- выбранное поле, строка или кнопка остаётся в светлом «окне»;
- белая выноска со стрелкой называет элемент и объясняет, что в нём проверять;
- панель расширения остаётся доступной, фон или Escape закрывают подсказку;
- автопоказ отключён по умолчанию, чтобы наставник не перекрывал рабочую страницу
  без явного действия оператора.

Состояния `ok`, `warning` и `info` остаются частью логики проверок, но не
превращают исходную страницу в постоянную зелёно-красно-синюю разметку.

На главной карточке контроль разделён на последовательные группы:

- **Интернет сейчас** — только однозначные маркеры: `online / active(n)` из Juniper,
  отрицательный остаток и явные блокировки доступа, пакета, состояния или группы.
  Нормальные значения Billing означают отсутствие запрета, но не подтверждают сессию.
- **Доступ и ограничения** — разрешённый/запрещённый доступ и административные
  ограничения. Зелёный ключ и поле «Авторизация: Выключена» не используются:
  фактическая текущая сессия определяется только по статусу Juniper;
- **Состояние услуги** — состояние карточки и неотрицательный день начала
  потребления услуг; критичные значения группы `Удаленные` и пакета
  `Заблокирован` переносятся в верхний блок однозначных маркеров;
- **Финансы** — остаток после учёта стоимости текущего тарифного плана;
- **Техническая проверка** — напоминание открыть Juniper и, для PON, опросить ONU
  в правильном разделе OLT.

В самом разделе «Технические данные» работает отдельный мини-курс:

1. `Технология подключения абонента` определяет маршрут: Ethernet/Wireless ведут в
   UserSide, PON — к проверке идентификатора ONU и OLT.
2. `Мак-адрес абонента` трактуется как MAC роутера или конечного устройства и не
   смешивается с `EPON ONU Мак-адрес` либо `GPON ONT Серийный ID`.
3. Для Ethernet пустые ONU/OLT являются штатным состоянием. Заполненное PON-поле при
   Ethernet выводится как противоречие.
4. Для PON требуется один соответствующий идентификатор: EPON MAC или GPON Serial.
   Пустой идентификатор, оба поля сразу либо несовпадение с типом OLT предупреждают
   оператора.
5. Распознанная OLT ведёт в BDCOM EPON, BDCOM GPON, GCOM или Huawei. Если OLT пустая
   либо неизвестна, оборудование сначала определяется по ТМЦ UserSide.

На странице Juniper наставник фиксирует один из четырёх явных исходов. Активная сессия
подтверждается status `online / active`, session ID, IP, MAC, VLAN и обменом. Если
сессия отсутствует, наставник в режиме GET сверяет главную карточку: при группе
`Удаленные`, пакете `Заблокирован` или запрещённом доступе отсутствие сессии считается
ожидаемым состоянием неактивной услуги. После просмотра результат и время сохраняются
для конкретного Billing ID и отображаются в техническом разделе главной карточки.
Визуальные состояния результата различаются: зелёное `active now`, жёлтый след
предыдущей сессии, серое ожидаемое отсутствие у неактивной услуги и красное
необъяснённое отсутствие сессии и каких-либо следов.
В активном состоянии технический аккордеон отдельно расшифровывает status/session ID,
BRAS/источник, IP–MAC–VLAN, время старта/последнее событие, трафик/скорость и
ROUTER/VENDOR. Клик по строке пункта раскрывает учебную заметку, а отдельная кнопка
подсвечивает соответствующую строку Juniper; пояснение явно отделяет доказанный факт
от подсказки или сетевого отпечатка.
Дословное поле `Статус сессии` вынесено отдельно: `online / active(n)` считается
прямым подтверждением текущей интернет-сессии, а `offline / inactive` или явное
сообщение об отсутствии сессии — прямым подтверждением её отсутствия.

Для выбора OLT наставник использует цепочку доверия: сначала в режиме только чтения
проверяет страницу «Технические данные» и сопоставляет поля `Технология подключения
абонента`, `OLT`, `EPON ONU Мак-адрес` и `GPON ONT Серийный ID` с разделами BDCOM
EPON, BDCOM GPON, GCOM и Huawei. Если PON подтверждён, но поле `OLT` пустое, наставник
получает карточку UserSide по штатной ссылке, читает ТМЦ и применяет тот же определитель
оборудования, что и автоматическая диагностика. Однозначный результат подсвечивает
нужный раздел опроса ONU; неоднозначный оставляет для ручной проверки без догадки.
Название тарифа само по себе не считается достаточным основанием для выбора OLT.

Для вывода ONU автоматически отмечаются VLAN, operational/admin state,
длительность работы, Rx/Tx и журнал причин/времени отключений. Пороговая оценка
оптики добавляется только после фиксации диапазонов по технологии и модели OLT.

### Единый разбор ответа ONU

Учебный режим не повторяет диагностические условия отдельно. Он вызывает общий
анализатор из `workbench.js`, который выбирает адаптер по действию Billing:

- `a=310` — BDCOM EPON;
- `a=311` — BDCOM GPON;
- `a=312` — GCOM;
- `a=313` — Huawei.

Результат анализатора разделяется на раскрываемые учебные блоки: состояние ONU,
выученный MAC, состояние Ethernet-порта, скорость и duplex, оптические уровни,
uptime и история включений/отключений. Ниже показываются три уровня интерпретации:
подтверждённые факты, отклонения и итоговый диагностический вывод. Клик по строке
открывает короткую заметку, «Подробнее» показывает полную трактовку, а отдельная кнопка
включает контрастный прожектор на соответствующей строке исходного ответа OLT.

Подсветка строится не по отдельным словам, а по связанным смысловым блокам:

- BDCOM GPON — MAC/VLAN/PON-порт, `Active Time + Active Duration`, состояние
  UNI-порта, `Online Duration + история отключений`;
- BDCOM EPON — прямое предупреждение о неверном MAC ONU вместе с таблицей MAC,
  текущая активная регистрация вместе с `LastRegTime/Alivetime`, отдельно понятный
  контекст предыдущего `LastDeregTime/Reason`, состояние порта и `RxPower`;
- Huawei — learned MAC, service-port/VLAN, состояние Ethernet-порта, оптика и
  длительность текущей регистрации;
- GCOM — состояние ONU, MAC, порт, оптика и история в доступном формате ответа.

Заголовок штатной страницы опроса используется как источник ожидаемых значений
`SN ONU / MAC ONU` и `MAC абонента`. Благодаря этому MAC самой ONU не подменяется
MAC роутера, а сообщение OLT о неверно указанном MAC становится отдельным конфликтом.
Исторический `wire-down`, `LOSi` или `dying gasp` не считается текущим offline, когда
активная таблица и рабочие OAM-статусы подтверждают текущую регистрацию.

Так автоматическая диагностика и обучение используют одну систему правил. Реальные
ответы каждой модели OLT всё равно нужны как регрессионные примеры для проверки
точности визуальной привязки строк после изменений формата Billing.

## Карта покрытия

| Область базы знаний | Текущее покрытие Workbench | Что добавить |
|---|---|---|
| Поиск абонента в UserSide и Billing | Основной поиск договора реализован | Контроль неоднозначного результата: одинаковый договор в разных системах, несколько договоров на один телефон, сверка адреса и ФИО |
| Точка коммутации | Для PON реализованы TMC, Billing-гипотезы и история MAC | Отдельные ветви для Ethernet-коммутатора и медиаконвертера |
| Активность OLT/коммутатора | Косвенно определяется успешностью запросов | Явная проверка ping, uptime, SNMP и состояния оборудования; различать неисправность и неуправляемое оборудование |
| Juniper | Используются параметры сессии и MAC для поиска | Полная интерпретация состояния, трафика, времени сессии и последнего события; безопасные подсказки для SYNC и CoA |
| Ethernet | Частично определяется Ethernet-link ONU | Полный сценарий для подключения витой парой: линк, скорость порта, MAC/FDB, ошибки, кабельный тест, трафик |
| PON | Самое сильное покрытие: поиск OLT, опрос ONU, status/link/MAC/оптика/history | Добавить состояния `authenticated` и `llid-admin-down`; сделать пороги сигналов зависимыми от EPON/GPON и направления |
| Уровни оптического сигнала | Сейчас используются общие пороги предупреждения и ошибки | Перенести технологические диапазоны из базы знаний и отдельно оценивать ONU Rx, ONU Tx и OLT Rx |
| Static IP | Специальной ветви нет | Определять статическую схему и показывать другой порядок диагностики без требования регистрации MAC |
| Медиаконвертер | Специальной ветви нет | Интерактивная расшифровка FX/TX/Link/Act/FDX/PWR и соответствующих рекомендаций |
| Регистрация MAC | Workbench сверяет зарегистрированный и фактически изученный MAC | В «Наставнике» добавить безопасный сценарий саморегистрации, проверку источника MAC и напоминание о времени применения |
| Кабельное телевидение | Не относится к текущей PON-диагностике | Готовый ветвящийся опрос: количество телевизоров, аналог/цифра, каналы, локальность проблемы, проверка аварии, данные для заявки |
| Создание заявки | Не является частью основной диагностики | Формировать проверенный черновик описания из ответов оператора, не отправляя заявку автоматически |

## Подтверждённые расхождения и точки усиления

### Сигналы PON

Текущая реализация применяет общие пороги:

- предупреждение при уровне не выше `-30 dBm`;
- критический уровень при значении не выше `-32 dBm`.

База знаний различает:

- EPON и GPON;
- входящий и обратный сигнал;
- хороший, допустимый и критический диапазоны.

Следовательно, оценка должна зависеть от технологии и направления сигнала. До переноса точных порогов их необходимо оформить как конфигурацию и подтвердить на актуальных ответах каждой модели OLT.

### Состояния ONU

Workbench уже понимает online/offline, потерю питания, потерю оптического сигнала и административное отключение. База знаний добавляет важные промежуточные состояния:

- `authenticated` — ONU получает конфигурацию; оператору нужно подождать и повторить проверку;
- `llid-admin-down` — возможен слабый сигнал или программная блокировка;
- `wire-down` — проверка оптики, патч-корда и LOS;
- `power-off` — проверка питания ONU.

Эти состояния подходят и для автоматического вывода, и для пошагового сценария «Наставника».

### Ethernet и Juniper

Workbench сейчас ориентирован прежде всего на PON. База знаний даёт полноценный Ethernet-сценарий:

1. Проверить получение настроек и состояние Juniper-сессии.
2. Проверить линк и скорость порта.
3. Сверить MAC/FDB.
4. Посмотреть ошибки порта.
5. При необходимости выполнить кабельный тест.
6. Проверить трафик.
7. Только после этого рекомендовать заявку или дальнейшие действия.

Это наиболее очевидный следующий диагностический модуль после PON.

## Первый сценарий режима «Наставник»: PON

1. Идентификация абонента.
   - Договор найден однозначно?
   - Адрес и ФИО совпадают?

2. Проверка контекста.
   - Есть ли открытая или массовая авария?
   - Какой тип подключения: EPON, GPON, GCOM или Huawei?

3. Состояние ONU.
   - Online.
   - `wire-down`.
   - `power-off`.
   - `authenticated`.
   - `llid-admin-down`.
   - Неизвестный статус.

4. Оптические уровни.
   - Показать фактические значения.
   - Объяснить направление каждого сигнала.
   - Оценить их по профилю технологии.

5. Связь ONU ↔ роутер.
   - Ethernet-link.
   - Скорость и duplex.
   - Наличие и соответствие MAC.

6. История.
   - Последнее отключение.
   - Повторяемость отключений.
   - Питание или оптическая линия.

7. Рекомендация.
   - Конкретные вопросы и действия для оператора.
   - Условие повторной проверки.
   - Основание для создания заявки.

8. Итог.
   - Какие проверки выполнены.
   - Какие данные подтверждены автоматически.
   - Что осталось непроверенным.
   - Подготовленный текст для поля «Описание».

## Формат сценариев

Сценарии не следует жёстко вписывать в UI-код. Их лучше хранить как отдельные правила:

```js
{
  id: "pon-onu-power-off",
  appliesWhen: {
    technology: ["epon", "gpon"],
    onuState: "power-off"
  },
  steps: [
    {
      id: "confirm-power",
      title: "Проверить питание ONU",
      explanation: "OLT сообщает о пропадании питания терминала.",
      questions: [
        "Горят ли индикаторы ONU?",
        "Есть ли электричество у абонента?",
        "Проверен ли блок питания и розетка?"
      ]
    }
  ],
  outcome: {
    retryAfter: "После восстановления питания повторить опрос ONU",
    escalateWhen: "Питание есть, но ONU не включается"
  }
}
```

Так правила можно:

- тестировать отдельно от интерфейса;
- обновлять без переписывания основной диагностики;
- переиспользовать в автоматическом отчёте;
- постепенно расширять новыми технологиями.

## Регрессионные тесты из базы знаний

База знаний превращается в набор проверяемых сценариев:

- `wire-down` → оптическая ветвь;
- `power-off` → питание;
- `authenticated` → ожидание и повторный опрос;
- `llid-admin-down` → сигнал/блокировка и заявка;
- ONU online + link down → кабель ONU–роутер или питание роутера;
- ONU online + link up + MAC mismatch → проверить регистрацию MAC;
- Ethernet link down → кабельный тест;
- несколько MAC на порту → неправильная локальная коммутация;
- Static IP → не требовать регистрации MAC;
- неисправность медиаконвертера → расшифровка по индикаторам;
- телевизионная проблема → обязательный набор вопросов перед заявкой.

## Безопасность материала

Исходные скриншоты нельзя напрямую включать в расширение. На них встречаются рабочие персональные и технические данные:

- ФИО и адреса;
- телефоны и договоры;
- IP- и MAC-адреса;
- логины и другие служебные значения.

Для расширения нужно использовать:

- обезличенный текст;
- собственные схемы;
- очищенные фрагменты интерфейса без идентификаторов;
- динамическое подсвечивание элементов непосредственно на текущей странице вместо сохранённых рабочих скриншотов.

## Рекомендуемый порядок разработки

1. Добавить инфраструктуру выбора и сохранения режима.
2. Вынести текущую автоматическую диагностику в профиль `auto`, не меняя её поведение.
3. Создать движок сценариев `mentor`.
4. Реализовать первый сценарий «Наставника» для PON.
5. Уточнить PON-пороги и состояния ONU в автоматическом режиме.
6. Добавить Ethernet + Juniper.
7. Добавить Static IP и медиаконвертер.
8. Добавить сценарий кабельного телевидения и генерацию описания заявки.
9. Покрыть все правила автоматическими тестами.
