# Процесс разработки

## Основная схема

`main` — стабильная версия, которую можно установить или упаковать. Каждая
функция, исправление или эксперимент разрабатывается в отдельной короткоживущей
ветке:

- `feat/<короткое-имя>` — новый модуль или возможность;
- `fix/<короткое-имя>` — исправление;
- `docs/<короткое-имя>` — только документация;
- `chore/<короткое-имя>` — сборка, тесты и обслуживание репозитория.

Одна ветка решает одну задачу. Это упрощает проверку, откат и разрешение
конфликтов.

## Как мы взаимодействуем

1. Пользователь описывает ожидаемое поведение, страницу/режим, пример входных
   данных и критерии готовности. Скриншот или лог прикладывается при необходимости.
2. Codex обновляет локальный `main`, создаёт отдельную ветку и сначала фиксирует
   текущее воспроизведение проблемы.
3. Изменение реализуется только в нужном модуле. Проверенная большая логика не
   разбивается и не переписывается без отдельной причины.
4. Добавляются или обновляются регрессионные тесты. Выполняется `npm.cmd test`
   в Windows или `npm test` в Linux/macOS.
5. Для изменений поведения проводится короткий live smoke-test в авторизованном
   Chrome по чек-листу `extension/docs/LIVE_VALIDATION.md`.
6. Изменения коммитятся осмысленным сообщением, отправляются в GitHub и
   просматриваются как diff/PR.
7. После успешной проверки ветка объединяется с `main`. ZIP собирается только из
   итогового коммита `main`.

Пользователю не нужно каждый раз пересылать весь проект. Достаточно указать
репозиторий, задачу и приложить только новые данные, лог или скриншот. Codex сам
забирает актуальную версию Git, вносит правку, тестирует и сообщает ветку, commit
и результат.

## Команды

```powershell
git switch main
git pull --ff-only
git switch -c feat/example

npm.cmd test
npm.cmd run package:extension

git add --all
git commit -m "feat: краткое описание"
git push -u origin feat/example
```

Перед объединением ветка синхронизируется с `main`. Конфликты разрешаются по
смыслу, после чего полный тестовый набор запускается заново. Не следует принимать
весь вариант `ours` или `theirs` для крупных файлов без просмотра diff.

## Версии и релизы

Версия Chrome Extension хранится в `extension/manifest.json` и синхронно в
`package.json`. Изменение только документации не требует новой версии.

- patch (`0.4.1` → `0.4.2`) — исправление без нового пользовательского сценария;
- minor (`0.4.x` → `0.5.0`) — новая функция или модуль;
- major (`0.x` → `1.0.0`) — стабильный публично определённый интерфейс/релиз.

Версия отдельного Userside-модуля хранится одновременно в `@version` и константе
`VERSION` внутри `.user.js`.

Релизный порядок:

1. обновить версии и `CHANGELOG.md`;
2. выполнить `npm.cmd test` в Windows или `npm test` в Linux/macOS;
3. выполнить авторизованный live smoke-test;
4. объединить в `main`;
5. создать Git tag;
6. собрать ZIP командой `npm.cmd run package:extension` в Windows.

## Что не коммитим

- ZIP и временные сборки;
- содержимое `node_modules`;
- логи с данными абонентов;
- cookie, токены, пароли и выгрузки с персональными данными;
- случайные копии из Temp/Downloads.

Если для диагностики нужен реальный ответ системы, в тест сохраняется минимальный
обезличенный fixture.
